BRB · Автоматические обновления через GitHub Releases

ПОЛЬЗОВАТЕЛЮ
1. Один раз распакуйте полный комплект и откройте BRB.exe. Исходная сборка: 1.0.0.
2. Настройки → Система → Обновление BRB. Укажите свой публичный репозиторий в виде имя/репозиторий или https://github.com/имя/репозиторий. Приватные репозитории, токены, черновики и pre-release не поддерживаются.
3. Отметьте «Проверять и скачивать автоматически» и нажмите «Сохранить источник». Это включает проверку сразу, при следующих запусках и затем раз в 6 часов. Без флажка доступна ручная команда «Проверить и скачать».
4. Закройте BRB и запустите тот же BRB.exe, когда новая сборка скачана. Менять ярлык или распаковывать архив повторно не надо. Клиентские загрузки, игры, профили и library.json обновляющий модуль не меняет.

КАК ЭТО УСТРОЕНО
Исходный BRB.exe по-прежнему лежит в папке установки. Новая версия сохраняется отдельно в %LOCALAPPDATA%\OrbitLauncher\updates\<ID установки>. Следующий запуск исходного файла передаёт управление проверенной версии. Обновляется сам лаунчер, включая встроенный интерфейс и нативный хост. Внешняя папка messaging и собственные SDK не перезаписываются: при несовместимом изменении внешних зависимостей издатель должен отдельно дать полный комплект. Если перенести исходный BRB.exe в другую папку, понадобится заново выбрать источник. Выключение автопроверки не удаляет уже подготовленную версию.

Канал по умолчанию не задан. BRB выполняет только BRB.exe из выбранного публичного репозитория, сравнивает SHA-256 с digest файла из API GitHub и проверяет формат Windows x64. Размер ограничен 128 МиБ. Это контроль целостности, а не подпись издателя. Указывать следует только доверенный репозиторий. Ошибки сети, неподходящий формат и незаконченные загрузки не заменяют рабочую версию.

ВОЗВРАТ
«Вернуться к исходной сборке…» → подтвердите, затем закройте BRB и откройте прежний ярлык. Также можно закрыть BRB и запустить ИСХОДНЫЙ файл из папки распаковки с параметром --brb-recover. Это отключит автопроверку и удалит выбор обновлённой версии, но не затронет пользовательские данные. Если файл новой версии повреждён или не запускается, загрузчик пытается открыть исходную сборку.

ИЗДАТЕЛЮ: ПЕРВЫЙ РЕЛИЗ
1. Создайте публичный репозиторий, куда вы имеете право публиковать релизы. Не включайте личные настройки, ключи, SDK Discord/Steam или их конфигурацию. Распакуйте СОДЕРЖИМОЕ source.zip в корень репозитория: рядом должны лежать go.mod, hostbin/, web/ и .github/workflows/release.yml, а не сам архив. Загрузите файлы, включая скрытую папку .github, и разрешите GitHub Actions. Аккаунт или токен в BRB вводить не требуется.
2. После проверки изменений создайте тег, например v1.0.1, на нужном коммите и отправьте его в репозиторий (git tag v1.0.1; git push origin v1.0.1). Workflow запускает тесты, собирает BRB.exe для Windows x64, встраивает номер версии и публикует стабильный Release с файлом BRB.exe. Не перезаписывайте тег и файл опубликованного выпуска: для следующего создайте новый номер. Защитите доступ к репозиторию, тегам и workflow.
3. Для ручной публикации: из исходников соберите тот же BRB.exe с GOOS=windows, GOARCH=amd64, CGO_ENABLED=0 и -ldflags="-s -w -H windowsgui -X main.releaseVersion=1.0.1"; добавьте его под точным именем BRB.exe в стабильный релиз v1.0.1, помеченный Latest. Тег должен соответствовать версии внутри бинарного файла. Обновления в .7z, .zip или файлах-описаниях лаунчер не устанавливает.
4. Проверьте с исходной версии 1.0.0: настройте репозиторий, дождитесь «К следующему запуску: 1.0.1», закройте и откройте исходный BRB.exe, убедитесь, что в настройках указано «Установлена 1.0.1». Затем проверьте возврат к исходной сборке.

Ни репозиторий, ни релиз не создаются самим лаунчером. Для тестов исходников не нужны пароли или рабочий аккаунт: сетевые ответы в тестах имитируются.
